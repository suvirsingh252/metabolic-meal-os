## P0 — Security (Dev A)

### A1. Production deployment is effectively unauthenticated (fail-open auth design)

**Where:** [middleware.ts](../middleware.ts), [src/lib/server/request-guards.ts](../src/lib/server/request-guards.ts) (`enforcePrivateDeployment`)

**Problem:** When `APP_AUTH_TOKEN` is unset, the code allows *all* traffic unless `PRIVATE_DEPLOYMENT_MODE` is explicitly `"false"` — i.e. the default posture is open. The production Vercel env (`.env.vercel.production.local` pull) has **no `APP_AUTH_TOKEN` and no `PRIVATE_DEPLOYMENT_MODE`**, and the app is deployed at a public URL (`https://metabolic-meal-os.vercel.app`). Today, anyone on the internet can:
- call `/api/analyze-meal` and burn our OpenAI quota,
- write arbitrary pages into our Notion Meals/Feedback/Ingredients databases via `/api/notion/save-meal`, `/api/notion/log-feedback`, `/api/notion/save-ingredients`,
- read household data via `/api/today`, `/api/dashboard`, `/api/notion/meals`,
- enumerate our Notion database IDs and full property schemas via `/api/diagnostics/notion` and `/api/diagnostics/notion-schemas`.

**Fix:**
1. Invert the default: when `APP_AUTH_TOKEN` is missing, **deny** (503) unless the operator explicitly opts out with `ALLOW_UNAUTHENTICATED=true` (rename away from the confusing `PRIVATE_DEPLOYMENT_MODE` double-negative; keep reading the old var for one release with a `console.warn`). Apply the same change in both `middleware.ts` and `enforcePrivateDeployment` — they must stay in lockstep (see A3 for deduplication).
2. Update `.env.example` and the README auth section.
3. Coordinate with the project owner to set `APP_AUTH_TOKEN` and `IOS_SHORTCUT_TOKEN` in Vercel production env **before** merging, since this change will lock out the deployed app otherwise. (A2 must land in the same release, or setting the token bricks the UI — read A2 before starting.)

**Tests:** extend `tests/rate-limit.test.ts` or add `tests/request-guards.test.ts`: missing token + no opt-out ⇒ 503; opt-out ⇒ pass; valid bearer/header ⇒ pass.

### A2. Enabling `APP_AUTH_TOKEN` breaks the entire browser UI (cookie accepted by middleware, rejected by route guards; no login flow)

**Where:** [middleware.ts:21-27](../middleware.ts), [src/lib/server/request-guards.ts:46-53](../src/lib/server/request-guards.ts), all client fetches (e.g. [src/app/today/today-client.tsx:141](../src/app/today/today-client.tsx), [src/app/planner/planner-client.tsx:82](../src/app/planner/planner-client.tsx))

**Problem:** Middleware accepts `Bearer`, `x-app-auth-token`, **or** the `app_auth_token` cookie. The per-route `enforcePrivateDeployment` accepts only the two headers — not the cookie. Client pages call `fetch("/api/...")` with no auth headers. Consequences:
1. Nothing in the codebase ever *sets* the `app_auth_token` cookie — there is no login page or token-entry flow, so a browser user can't authenticate at all.
2. Even with the cookie set manually, every guarded API route returns 401 because the route guard ignores cookies.

So the moment A1's token is configured, the web app is unusable.

**Fix:**
1. Add cookie acceptance to `enforcePrivateDeployment` (read the `cookie` header; route handlers receive a standard `Request`, so parse `app_auth_token` from it — keep it dependency-free).
2. Add a minimal token-entry flow: a `/login` page (excluded from middleware matcher) with a form that POSTs the token to a small `/api/auth/session` route, which verifies it against `APP_AUTH_TOKEN` and sets `app_auth_token` as an `HttpOnly; Secure; SameSite=Lax; Path=/` cookie. On failure return 401. Middleware should redirect unauthenticated *page* requests (HTML `Accept` header) to `/login` instead of returning JSON 401.
3. Keep returning JSON 401 for `/api/*` requests.

**Tests:** guard accepts cookie; login route sets HttpOnly cookie on correct token and 401s on wrong token.

### A3. Deduplicate the auth check + use constant-time token comparison

**Where:** [middleware.ts](../middleware.ts), [src/lib/server/request-guards.ts](../src/lib/server/request-guards.ts), [src/app/api/intake/share/route.ts:16-36](../src/app/api/intake/share/route.ts)

**Problem:** The token-check logic exists in three places and has already drifted (that drift *is* bug A2). All comparisons use `===`, which leaks timing information for secret tokens.

**Fix:**
1. Create `src/lib/server/auth.ts` exporting a single `isAuthorizedRequest(request, { allowCookie })` used by middleware, `enforcePrivateDeployment`, and the intake route's `validateToken`.
2. Compare tokens with a constant-time helper. Note middleware may run on the Edge runtime where `node:crypto.timingSafeEqual` is unavailable — implement a small constant-time string compare (hash both sides with SHA-256 via WebCrypto, or XOR-accumulate over equal-length buffers) rather than importing `node:crypto`.
3. Do A3 after A1/A2 so you're consolidating the corrected logic.

### A4. `/api/intake/share` has no rate limit

**Where:** [src/app/api/intake/share/route.ts](../src/app/api/intake/share/route.ts)

**Problem:** Every other mutating route goes through `guardApiRequest`. The intake route validates its own bearer token but applies no rate limiting, so the token can be brute-forced and the endpoint can be used to flood the Notion intake database.

**Fix:** After `validateToken`, call `enforceRateLimit({ key: \`intake-share:${getClientIp(request)}\`, limit: 20, windowMs: 60_000, action: "intake-share" })`. Also validate `sharedAt`: it is user-supplied and passed straight into a Notion date property — reject non-ISO-8601 strings with a 400 instead of letting Notion 500.

**Tests:** add a case to `tests/intake-share.test.ts` for the rate-limit path and invalid `sharedAt`.

## P1 — Hardening (Dev B)

### B1. `/api/ingredients/lookup` bypasses all request guards

**Where:** [src/app/api/ingredients/lookup/route.ts](../src/app/api/ingredients/lookup/route.ts)

**Problem:** This route has no `guardApiRequest` (no auth, no rate limit) and uses raw `request.json()` with no body-size cap. It proxies to the FoodData Central API, so it can be used by anyone to exhaust our FDC quota. Compare with `/api/ingredients/enrich`, which does this correctly.

**Fix:** Mirror the enrich route: `guardApiRequest(request, { rateLimitKey: "ingredients-lookup", rateLimit: 30 })` and `readJsonWithLimit(request, 10_000)`. Keep existing validation.

### B2. Diagnostics routes need in-route guards

**Where:** [src/app/api/diagnostics/notion/route.ts](../src/app/api/diagnostics/notion/route.ts), [src/app/api/diagnostics/notion-schemas/route.ts](../src/app/api/diagnostics/notion-schemas/route.ts)

**Problem:** Both GET handlers rely solely on middleware. Middleware is currently fail-open (A1), and middleware matchers are an easy thing to regress. These routes return Notion database IDs, titles, and complete property schemas — exactly what an attacker writing to our Notion would want. Defense-in-depth says guard them in-route like every other data route.

**Fix:** Add `guardApiRequest(request, { rateLimitKey: "diagnostics", rateLimit: 10 })` to both handlers (change signatures to accept `request: Request`).

### B3. `MemoryRateLimiter` map grows without bound

**Where:** [src/lib/server/rate-limit/memory.ts](../src/lib/server/rate-limit/memory.ts)

**Problem:** Buckets are keyed by `route:ip` and never evicted — an expired bucket is only replaced if the *same* key returns. A scanner cycling spoofed `x-forwarded-for` values grows the Map indefinitely for the life of the server process.

**Fix:** Opportunistic sweep: on each `check()`, if `buckets.size` exceeds a threshold (e.g. 10k) or every N seconds, delete entries with `resetAt <= now`. Keep it dependency-free and O(n) only on sweep. Add a test that expired buckets are evicted.

**Also note in code:** this limiter is per-process; on Vercel each serverless instance has its own Map, so limits are best-effort. Add one comment stating that constraint (an upstash/durable implementation is a future ticket, not this one).

### B4. `decodeHtmlEntities` mishandles astral code points

**Where:** [src/lib/integrations/recipe-parser/index.ts:978-992](../src/lib/integrations/recipe-parser/index.ts)

**Problem:** `String.fromCharCode` breaks for code points above U+FFFF (e.g. `&#x1F35C;` 🍜, common in recipe titles/captions) — it produces garbage instead of the emoji. Also guard `Number.parseInt` results: a huge numeric entity yields `NaN`/invalid code point and `fromCodePoint` would throw.

**Fix:** Use `String.fromCodePoint` wrapped so invalid/out-of-range values fall back to returning the original entity text. Add cases to `tests/recipe-url-security.test.ts` or a new parser test file.

### B5. Consolidate duplicated Notion route helpers (existing tech-debt item — now scheduled)

**Where:** `isRecord`, `getPrimaryDataSourceId`, `getDatabaseTitle`, `getNotionPageUrl`, `validationError` duplicated across [src/app/api/notion/save-meal/route.ts](../src/app/api/notion/save-meal/route.ts), [src/app/api/diagnostics/notion-schemas/route.ts](../src/app/api/diagnostics/notion-schemas/route.ts), [src/app/api/diagnostics/notion/route.ts](../src/app/api/diagnostics/notion/route.ts), [src/lib/intake/notion.ts](../src/lib/intake/notion.ts), and others.

**Fix:**
1. Create `src/lib/notion/route-helpers.ts` (or extend `src/lib/notion/mappers.ts`) with the shared helpers; replace local copies. No behavior change — this is a pure extraction, verify with the existing test suite.

The existing `tests/nutrition-notion-mapping.test.ts` and `tests/meal-validation.test.ts` must stay green.
